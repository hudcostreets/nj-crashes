# `/tune/ab` preference stream → learned picker thresholds

## Motivation

Picker tuning by "edit a constant, eyeball one view" silently skews other views (see the `scopedTargetFactor` episode). And the v1 `/tune/ab` flow — Ryan authors a candidate config, the page diffs it against shipped — had the roles backwards: the human shouldn't have to hypothesize configs.

v2 inverts it: the page generates side-by-side comparisons, Ryan only expresses preference, and translating the accumulated "vibes" into picker parameters (thresholds / a decision tree over `{viewport, zoom, bins returned, clip share, …}`) is Claude's offline job.

## Collection (implemented; v5)

- `/tune/ab` samples a view, computes the shipped picker's level `prod` for it, and renders that against an adjacent level (`prod±1`, direction random, sides randomized).
- **No deck** (v5). Views are *sampled*, not enumerated — Ryan: "you could just generate views at ~random, not have to list 42 ahead of time". A hand-written list also encodes a guess about which views matter, which is the guess the corpus exists to test. Each pair draws:
  - a **scope** from `www/src/map/tune-scopes.json` — one row per thing the real app can scope to (statewide, 21 counties, 564 munis = 586), generated by `njdot tune scopes` from `www/public/Municipal_Boundaries_of_NJ.geojson` with measured center, bbox half-extents, `km2`, population, and the zoom at which it fits a reference viewport;
  - a **viewport** from {embed 1280×480, full 1470×900, phone 390×700} — `areaPx` is the picker's main input and swings 4× across these;
  - an **off-center pan** (±0.35 of the scope's half-extents; ±0.15 statewide), because real users don't sit on the centroid;
  - a **zoom**, continuous, in a window relative to the scope's fit zoom refitted to the sampled viewport: `[-0.4, +5.0]` for counties, `[-0.4, +3.5]` for munis, `[-1.5, +1.5]` statewide. Below fit the scope stops filling the frame (so the scoped budget stops describing the view); above it is a user zooming in, through to street scale where the `minTargetPx` clamp stops binding.
- **Stratified by scope kind**, not by scope: the draw goes to whichever of {statewide, county, muni} has the fewest recorded votes. Per-scope coverage is unreachable at 586 and isn't what the fit needs — it conditions on the scale regime, so what has to stay balanced is the regimes, not the geography. Within a kind, scopes are weighted by `pop ** 0.75`: uniform over 564 munis draws mostly rural boroughs with no crashes to look at, and straight population draws Newark every time.
- **Sparse draws auto-resample.** If neither side clears `MIN_CELLS` (400) once both have loaded, the page samples a new pair (bounded at 12 consecutive skips, so a broken sampler surfaces instead of looping). A frame with a dozen sub-pixel dots on black isn't something to have a preference about, and a vote collected on one is noise the fit would take seriously. Pinned pairs (`?v=` in the URL, or `open` from history) are exempt.
- A vote's `view` is the scope **slug** (`c-hudson`, `m-hudson-hoboken`, `nj`), and the row also carries the sampled center and viewport, so any row reconstructs its exact pair. Rows written before v5 hold a display name instead; they still fit (the fit conditions on recorded features, not names) but don't reopen.
- **Informed voting** (v2.1, replacing the original blind design): each side's corner label shows its level, geom/inscribed/render px, cells, body + wire bytes, and perceived load ms — Ryan: "i'll want to take those metrics into account in some cases."
- Verdicts: `1` left · `2` tie · `3` right · **`4` neither — want finer than both** · **`5` neither — want coarser than both** · `s` skip (not recorded). The directional "neither" verdicts capture sweet-spots outside the shown pair (e.g. statewide-mid where both l12 and l13 read "too griddy"). An optional free-text note rides along with each vote.
- Voting is gated until both sides' cells have loaded, so recorded metrics are real.
- Votes live in the **`tune` D1 database** (`picker_votes` table, schema `cells-api/sql/tune.sql`), served by the cells-api worker: `GET /v1/tune/votes[?limit=&view=]` (public), `POST /v1/tune/votes`, `PATCH /v1/tune/votes/<id>` (both require `Authorization: Bearer $TUNE_TOKEN`). Columns are flat so the corpus is queryable in SQL — analysis is `wrangler d1 execute tune --remote --command "SELECT …"`, not a JSONL parse.
  - Writes **fail closed**: no `TUNE_TOKEN` secret on the worker ⇒ writes refused. The client sends `VITE_TUNE_TOKEN` from the gitignored `www/.env.local`.
  - The `voter` column is the seam for **$oa/auth**: token writes record NULL (the local admin); logged-in voters would record their identity, which is what lets others participate in admin-ish actions like this. (v2 kept votes in a git-tracked JSONL; Ryan: "I definitely don't want a Git-tracked jsonl pretending to be a DB" — it is gone.)
- The current pair is URL-encoded, golfed but readable: **`?v=<scope-slug>&z=<zoom>&y=<lat>&x=<lon>&p=<vp>&l=<level>&r=<level>`** (e.g. `?v=c-warren&z=12.60&y=40.7960&x=-74.9293&p=e&l=17&r=16`). Continuous sampling means the slug alone no longer reconstructs a pair, hence the center and viewport. Floats use `floatParam`'s string encoding (2 decimals of zoom, 4 of lat/lon) rather than the default base64.
- A **history panel** lists votes newest-first, 25 per page (chosen side highlighted); choice is editable in place (PATCH stamps `edited_ts`, shown as a `*`), and `open` reloads that row's exact pair.

### Vote wire schema

```json
{
  "id": 1,
  "ts": "2026-08-22T…",
  "editedTs": null,
  "voter": null,
  "view": "Hudson county fit",
  "lat": 40.73, "lon": -74.09, "zoom": 10.93,
  "vp": [1470, 900],
  "scopeKm2": 120,
  "mppx": 33.1,
  "areaPx": 109000,
  "autoTargetPx": 1.04,
  "cfg": { "targetFactor": 0.85, "pickMult": { "20": 0.55, "21": 0.4 } },
  "prod": 17,
  "left":  { "level": 17, "bins": 13300, "bodyBytes": 2300000, "wireBytes": 152000, "ms": 3283 },
  "right": { "level": 16, "bins": 5400,  "bodyBytes": 930000,  "wireBytes": 78000,  "ms": 2555 },
  "choice": "left",
  "chosen": 17,
  "note": ""
}
```

`cfg` snapshots the shipped config at vote time, so rows remain interpretable as `tuning.json` evolves. `chosen: null` ⇔ tie/finer/coarser. `choice ∈ {left, right, tie, finer, coarser}`. `wireBytes: 0` means unknown — it needs the cells-api worker's `Timing-Allow-Origin: *` header (`cells-api/src/index.ts`, deployed 2026-08-22).

## Learning — `njdot tune` (implemented)

`njdot/cli/tune.py` is the offline half. It reads the corpus from the votes
endpoint (`-c <path>` caches the raw JSON so a session isn't refetching), and
parses `S2_DIAMETER_METERS`, `BINS_BUDGET` and `tuning.json` straight out of
the frontend sources — the picker math is ported, but not the *constants*, so a
change on the TS side can't silently desync the fit.

- **`njdot tune votes`** — per-view outcome table: prod wins / alt wins / ties /
  finer / coarser, signed directional pressure, median bins of the chosen side.
- **`njdot tune levels [view]`** — per-vote: what the shipped config picks vs
  what was preferred, with `mppx` and the budgeted target px.
- **`njdot tune fit [-m]`** — grid-search over `targetFactor` × `minTargetPx` ×
  per-level `pickMult`, scored as "how many recorded preferences would this
  config have honored". Candidates that predict identically on the corpus are
  collapsed to their simplest representative, and ranking prefers configs that
  leave `pickMult` alone (per-level multipliers fit to a handful of votes at
  one boundary are the easiest way to overfit). `-m` lists the votes the winner
  still violates — the most useful output, since it names what to collect next.

A vote is *honored* if the config picks the chosen level; for `tie`, either
shown level; for `finer`, any level above the pair; for `coarser`, any below.
Contradictory votes are expected, not noise — near a boundary, preference is
probabilistic. Only propose a change where the direction is consistent (≥70% of
decisive votes in a region, n ≥ ~10) and prefer the smallest config move that
captures it. Validate before shipping by re-running the stream with the pair
generator set to `shipped-pick vs candidate-pick` (the v1 config-diff mode,
resurrectable with a small generator swap) — one CIC at one viewport is
spot-checking, not evaluation.

### What the first 32 votes said

The corpus splits cleanly into two regimes, and the split is structural rather
than statistical: `autoHexPxTarget` clamps its target to a floor, and for
**every** county/muni-scoped view the budgeted `areaPx` is small enough that the
clamp binds — their level comes from `minTargetPx` alone, while statewide and
street views run above the clamp and see only `targetFactor`.

- **Statewide wants finer**: 6 of 9 decisive statewide votes ask for a level
  above prod (5 of them the "neither — want finer" verdict, noted *griddy*);
  none ask for coarser.
- **Street wants finer**: 2 of 2.
- **Scoped views are right where they are**: Cape May 7/7 prod, Hudson 4/4 prod,
  Jersey City 4/5. The two exceptions are Hoboken, which wants *coarser*.

A single `targetFactor` can't express that — it multiplies both regimes — which
is why the v3 grid search (one knob) topped out at 21/32. Fitting the floor as
its own knob separates them: **`targetFactor` 0.85 → 0.45, `minTargetPx` 1.0 →
1.9** takes the shipped config from **19/32 (59%) to 27/32 (84%)**. Note the
product is nearly unchanged (0.85 → 0.855), which is exactly the point: scoped
views stay put, statewide moves one level finer. Adding `pickMult[19] ≈ 0.2-0.5`
reaches 29/32, but that's a third knob fit to 9 muni votes — collect more
Hoboken/JC-muni votes before believing it.

The free-text notes say something the choice column can't. Every *griddy* note
(4) rides a "want finer" verdict — aesthetic complaint, resolved by moving a
level. Every *too much data* note (5) rides a vote that picked **prod or finer**
(4 prod, 1 finer) — i.e. it is not a request for coarser bins, it's a complaint
about what a bin costs. The two axes are orthogonal and the current UI collapses
them into one: a voter who thinks "this looks right but shouldn't cost 15 MB"
has only the level dial to say it with. Worth recording separately — a
per-side "cost unacceptable" toggle alongside the level preference — since
that's the signal that argues for the wire format rather than for the picker.

**Not shipped**, because it's in direct tension with the other finding of the
same session: statewide one level finer is ~3× the cells, and the same votes
carry "too much data" notes. `minTargetPx` is now a real knob
(`www/src/map/tuning.json`), defaulted to the current 1.0 so nothing moved. The
sequencing is `specs/cells-compact-wire-format.md` first (a bin costs ~16 gz B
today, ~4 under the columnar format), then honor the preference.

## Possible extensions

- **Online adaptation** — currently the loop is deliberately offline: votes accumulate, `njdot tune fit` proposes, a human ships `tuning.json`. Auto-applying the fit would mean the picker drifts under the voter mid-session, which both invalidates the corpus (`cfg` is snapshotted per row for exactly this reason) and makes regressions untraceable. A middle option worth having: a `?cfg=` override on `/tune/ab` so a candidate can be *voted against* before it ships, which is also the validation step above.
- Real clip polygons instead of the scope table's `km2` scalar (measured per admin polygon, but still a scalar — the true `polygon ∩ viewport` area is what prod budgets, and it diverges most exactly where the sampler pans off-center).
- Weight scopes by actual crash counts rather than population. `njdot tune scopes` runs where `njdot/data/crashes.parquet` lives, so a per-`(cc, mc)` join is available; it needs the muni-code harmonization to match the GeoJSON's `NAME`/`COUNTY`, which is why v5 uses population as the proxy.
- Reverse/threshold mode (Ryan's other idea): display each level's current min/max zoom ranges across several counties with draggable thresholds and a "this feels right" commit — an extension of `/tune` (which already computes `zoomRangeForLevel`) rather than of the vote stream.
- Deck growth: more counties, off-center views, DF-mode / render-curve A/Bs (would need `renderMode` variants in the pair, recorded in rows).
- Weight recent votes over old ones once configs shift substantially.
